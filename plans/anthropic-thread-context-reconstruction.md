# Reconstruct Anthropic thread requests into full canonical context

## Status and objective

**Proposed; not implemented.** Materialize the client-visible accumulated context of short Anthropic `thread` requests in Python, then derive their input blocks and category estimates from that canonical JSON. Keep the original wire request separately. A successful reconstruction should make a short continuation inspectable like a full-history Messages request, without claiming to know provider-internal content that was not observable.

The existing OpenAI Responses/Codex WebSocket normalizer is the architectural template: normalize provider state before analysis, follow an explicit provider response ID, persist canonical request/response documents, and mark unavailable or opaque history honestly. The Anthropic continuation grammar must be validated separately; copying the Responses `input + output + input` algorithm would be an assumption, not an implementation.

## Why this is needed

In session `e915df9d-0f4b-4302-b8aa-a4a94efabae2`, request #382 is a `thread.create` with two messages and 14 tools. #383–#398 are `thread.continue` calls with short message deltas and usually no tool definitions. #398 currently has 199 locally estimated visible input tokens, while the provider reports 62,326 input tokens, including 61,790 cache-read and 534 cache-creation tokens. #399 drops `thread` and sends a full 55-message, 14-tool history. The short rows are currently stored with `context_fidelity="complete"`, no `predecessor_response_id`, and canonical JSON equal to their short wire bodies. Thus the adapter correctly describes the **transmitted delta**, but not the accumulated visible context. #384 references a message ID not found among retained predecessor responses, so even this example cannot be reconstructed perfectly end-to-end without more evidence.

The provider token figure does **not** prove every token was retransmitted over the network. Prompt-cache accounting and thread-state transport are separate concepts. Reconstructing blocks should improve content coverage; it will not make local `tiktoken` estimates equal Anthropic's tokenizer/usage numbers.

## Contracts and boundaries to establish first

1. **Two request documents.** `raw_request_body` remains the exact short wire JSON. `canonical_request_body` becomes the expanded, provider-shaped, client-visible logical request analyzed by the Anthropic adapter. It must be clear in API/docs that canonical is a reconstruction, not bytes sent on the wire or a guarantee of the exact post-edit model prompt.
2. **One exact predecessor source.** `thread.previous_message_id` is the candidate state predecessor for `thread.continue`; resolve it only against a matching provider response ID. `diagnostics.previous_message_id` is for cache-fingerprint comparison, **not** a context-lineage key. Never fill a missing link from temporal adjacency, model, or conversation grouping.
3. **Fidelity has meaning.** `complete` means all *observable logical* context needed by the supported reconstruction rules is retained. `partial` means a predecessor, response content, or required control state is missing. `opaque` means a known provider transformation or hidden content cannot be represented exactly. Notes should name the reason. Server-side context edits may change the actual prompt after the logical request is assembled.
4. **No frontend derivation.** The normalizer creates canonical JSON; the existing Anthropic adapter/classifier produces blocks, categories, tool statistics, and local estimates; the UI only displays these plus provider usage/fidelity. An inherited block must appear once, in its original chronological position.
5. **Non-thread requests stay unchanged.** Gate the new behavior on the observed `thread` shape, not every Anthropic-format request or every Claude model. Preserve existing behavior for ordinary Messages traffic and other providers/gateways.

The public [Messages API reference](https://platform.claude.com/docs/en/api/beta/messages/create) currently documents `diagnostics.previous_message_id` but does not document this captured `thread` request field. The rules below are therefore a hypothesis to verify against safe fixtures and observed full replays. [Anthropic's cache diagnostics guide](https://platform.claude.com/docs/en/build-with-claude/cache-diagnostics) confirms that the diagnostics ID compares prompt fingerprints; [context-editing documentation](https://platform.claude.com/docs/en/build-with-claude/context-editing) says edits run server-side before the model sees the prompt.

## Implementation sequence

### 1. Characterize the thread protocol and freeze fixtures

- Extract privacy-safe, synthetic fixtures for `create`, successive `continue`, tools/tool results, thinking/redacted thinking, mixed message roles, a branch from an older response, and a later full-history replay. Use real capture only for shape/ID/count assertions; do not commit personal prompts, tool outputs, cache keys, or message IDs.
- Establish whether `continue.messages` are an append-only delta, how the predecessor's assistant `content` is projected into a `messages` turn, whether omitted `system`/`tools` are inherited, and how present, empty, and null fields differ. Inspect response completeness and any returned thread/configuration metadata. Verify ordering across multiple user/assistant/tool turns and whether a continuation can replace or clear earlier content.
- Compare an uninterrupted synthetic reconstructed chain with a semantically equivalent explicit full-history request, both as JSON and as ordered blocks/category totals. Use #399 as a useful real-world cross-check, **not** proof of exact equivalence for #398 because the #384 predecessor gap and possible context edits remain.
- Record a field-by-field rule table for `messages`, `system`, `tools`, `model`, cache controls, `context_management`, diagnostics, and output-only settings. Do not inherit all top-level fields wholesale; carry only state that the protocol actually retains. If the observed protocol cannot establish a field's semantics, make that case partial/opaque rather than guessing.

**Gate:** do not label a thread reconstruction `complete` until the fixtures establish its append/inheritance rules. If the provider's thread semantics remain undocumented or untestable, ship a conservative best-effort expansion with explicitly limited fidelity.

### 2. Add an Anthropic normalizer before block analysis

- Add a focused `AnthropicThreadInvocationNormalizer` in `contextspy/normalization.py` (or a small provider-specific module) and register it for the adapter's `anthropic` protocol. Keep the identity path for requests without `thread`.
- For `thread.create`, retain the complete observed request (unless validation shows a stateful control needs a canonical adjustment) and capture the returned message ID. For `thread.continue`, resolve `thread.previous_message_id` via `InvocationLineageRepository`; set `predecessor_response_id` even when resolution fails, so diagnostics can show an unresolved **exact** reference.
- For a verified continuation, build the canonical message list from the predecessor's **canonical** messages, the predecessor's retained assistant response content as one message/turn according to the validated grammar, and the current observed message delta. Merge inherited `system`/`tools` only according to the field-rule table. Use deep copies and preserve exact content-part order, tool-use IDs, cache markers, thinking/redacted blocks, and any mid-conversation controls supported by the adapter. Strip the stateful `thread` control from a standalone canonical request while retaining it in the raw body and exact predecessor metadata.
- Do not treat response usage, diagnostics, stop metadata, or the entire response envelope as prompt content. Do not duplicate a predecessor output already present in the current delta. Support a response that contains tool calls, a partial assistant prefill, or an incomplete/error outcome only where the protocol gives enough evidence.
- Preserve `message_delta.context_management`/`applied_edits` in the Anthropic SSE response reconstruction when present; the current adapter merges delta and usage but does not copy that separate event field. Without it, a streamed response can lose the very evidence needed to distinguish an applied server edit from an edit merely configured in the request.
- Keep provider ID lookup unambiguous. The current repository picks the latest `(provider, response_id)` row; for this feature, detect collisions and reject an ambiguous predecessor rather than silently choosing one. Legitimate exact links across ContextSpy sessions should remain possible. Review whether provider namespace alone is sufficient for gateways/accounts before relaxing this rule.
- Make the reconstructed canonical document the sole input to `analyze_invocation`. The Anthropic adapter should need little or no new composition logic; add adapter support only for newly observed content-part types or verified context controls. Persist canonical request/response, provider and predecessor IDs, fidelity/notes, ordered `BlockRecord`s, category totals, and tool statistics through the existing pipeline.

### 3. Handle unavailable and provider-edited context explicitly

- Missing predecessor, duplicate ID, purged predecessor body, incomplete predecessor output, or a partial ancestor: keep all observable current content, attach the exact referenced ID, mark `partial`, and do not synthesize absent messages/tools. Propagate that limitation to descendants until a verified full-history reset provides a new anchor.
- Hidden/redacted thinking, opaque content, or an applied provider-side context edit whose affected blocks cannot be identified exactly: preserve the visible logical history but mark `opaque` (or `partial` if history itself is missing). Distinguish an *edit configured* from an *edit actually applied* using response evidence where available. Never delete thinking/tool-result blocks merely from a requested edit configuration or a token-count difference.
- Full-history non-thread requests are independent canonical anchors; they may resume reliable later reconstruction. Do not rewrite earlier short requests using a later replay unless equivalence is proven, because that would assign future knowledge to past requests.
- Preserve provider-reported `input_tokens`, cache-read, cache-creation, and output usage unchanged. Show the reconstructed local visible estimate as an estimate, not a billing correction. The gap can still contain tokenizer differences and server-only transformations.

### 4. Backfill retained historical rows safely

- Add an explicit versioned data migration (`db/migrations.py`, next `SCHEMA_VERSION`) for retained Anthropic thread rows. Re-read their **raw** request and retained canonical/response evidence, process roots and exact descendants topologically, then recompute canonical JSON and all derived blocks/category/tool columns using the same normalizer as live capture. Do not use row order as a substitute parent. Make re-runs idempotent and preserve old derived data on parser failure.
- No new column is required for the basic design: existing `provider_response_id`, `predecessor_response_id`, `context_fidelity`, `context_notes`, and canonical/raw bodies carry it. If protocol validation requires durable thread provenance beyond retained raw bodies, add a narrowly scoped field, the additive `_migrate()` column step, and the data migration together.
- Retention deletes raw **and canonical** bodies after the configured window. Rows already purged cannot be truthfully expanded. Leave their content/indexes intact; do not manufacture history from token usage. Mark them as unverifiable/partial with an explanatory note if the migration can identify them safely, and document that complete historical recovery is impossible after retention. Prevent a supposedly `complete` state from being inferred solely from surviving token counts.
- Run `contextspy db-upgrade` with the backend stopped, a verified SQLite backup, and an explicit migration report: rows expanded, already-full, missing ancestor, purged, failed, and estimated DB growth. The current backup helper copies the DB file; coordinate its safety with the postponed WAL/DB-lock plan before enabling WAL or relying on a file-only copy. Avoid a long write transaction during live proxy capture.

### 5. Verify UI, lineage, performance, and documentation

- On request detail and context panels, verify the reconstructed canonical JSON and inherited blocks are visible, with correct chronology, category totals, tool names, cache flags, and fidelity explanation. Keep a way to inspect the raw short request. The dashboard/session views should gain the exact parent link from `predecessor_response_id` without a new frontend grouping algorithm.
- Test create/continue chains, branches, missing and duplicate IDs, cross-session exact parent, tool-loop continuations, inherited/overridden/cleared system and tools, failed/incomplete SSE, hidden thinking, applied context edits, purged raw data, full-replay reset, migration idempotence, and unchanged ordinary Anthropic/OpenAI behavior. Add a regression reproducing the structural facts of #382–#399, including the #384 gap, without using private content. Run `pytest`; run frontend tests/build only if UI code changes.
- Benchmark capture and backfill at 100, 1,000, and 2,000 requests. Full canonical snapshots are inherently repetitive even though block contents are deduplicated; measure canonical bytes, DB growth, normalization latency, memory, and read/UI latency before release. Add a bounded read/cache or compression strategy only if measured, while preserving the promised full canonical JSON contract. Avoid recursive whole-chain DB traversal per live request; one predecessor canonical snapshot should suffice.
- Update `docs/transport-normalization.md`, `docs/development.md`, and user-facing request-tracking documentation with the wire-vs-canonical distinction, exact thread lineage, retention limit, server-edit/opaque limit, and provider-vs-local token accounting.

## Release criteria

1. A fully captured, validated thread chain yields the same ordered input blocks and category breakdown as its equivalent explicit full-history request; a short raw continuation remains inspectable as raw JSON.
2. Every `thread.continue` stores its provider predecessor ID. Missing, collided, incomplete, or purged ancestors never appear as fully reconstructed context and never acquire an inferred substitute.
3. #382–#398 gain substantially fuller representation where retained evidence allows it; the #384 gap and all downstream uncertainty remain visible. No claim is made that local estimates must equal Anthropic's reported tokens.
4. Non-thread traffic, OpenAI/Codex normalization, and conversation grouping regressions pass. Migration is recoverable, reports skipped rows, and does not silently erase existing analysis.
5. Performance and storage at the agreed normal upper bound of about 2,000 requests are measured and documented; provider-specific reconstruction remains entirely in Python.
